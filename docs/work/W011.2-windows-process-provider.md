# W011.2 — Windows Process Provider

## Status

Done on merge.

## Objective

Implement a Windows-native `ProcessProvider` behind W010 and validate it with a
controlled child process on the hosted Windows runner.

## Scope

- Add requested-PID inspection under `platform::windows` using documented
  Win32 process APIs.
- Return W006 process identity evidence with honest per-field availability.
- Reuse W009's Microsoft `windows-sys` dependency with only the required
  target-specific API feature addition.
- Validate W010 contract and W011 orchestration behavior with a controlled
  child and test-owned resources.
- Update architecture, testing, security, and this work record.

Tauri IPC, frontend changes, refresh coordination, elevation, and changes to

## Design Notes

### API feasibility

| Field                | APIs evaluated                                                                       | Selected mechanism                                                                | Support status                                                                                         | Limitation                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| PID / existence      | `OpenProcess`, process-object wait state                                             | One held process handle and zero-timeout `WaitForSingleObject` before/after reads | Available for accessible nonzero PIDs                                                                  | PID is a lookup key; the handle anchors only this inspection                                                       |
| Name                 | image path; Toolhelp enumeration; WMI `Win32_Process.Name`                           | `Path::file_stem` of verified image path                                          | Available when image path is available                                                                 | Basename without extension; no localized display-name semantics                                                    |
| Executable           | `QueryFullProcessImageNameW`; `GetModuleFileNameExW`                                 | `QueryFullProcessImageNameW` using Win32 path format                              | Best effort; `Unavailable(PermissionDenied/Inaccessible/ProviderLimitation)` on field query limitation | Bounded at 32,768 UTF-16 code units; availability may vary for protected processes                                 |
| Start time           | `GetProcessTimes`; WMI `CreationDate`                                                | `GetProcessTimes` creation `FILETIME`                                             | Available when query succeeds                                                                          | 100 ns source units normalized to `SystemTime`; still evidence, not authorization                                  |
| Structured arguments | `GetCommandLineW`; WMI `Win32_Process.CommandLine`; `CommandLineToArgvW`; remote PEB | No mechanism selected                                                             | `Unavailable(ProviderLimitation)`                                                                      | Current-process API is not arbitrary-process inspection; a command-line string cannot prove target argv boundaries |
| Working directory    | `GetCurrentDirectoryW`; WMI `Win32_Process`; remote PEB                              | No mechanism selected                                                             | `Unavailable(ProviderLimitation)`                                                                      | No supported public arbitrary-process current-directory query was identified; never infer it                       |

Microsoft documents `OpenProcess` with PID zero as a special failure:
System Idle Process produces `ERROR_INVALID_PARAMETER`, while protected system
targets can produce `ERROR_ACCESS_DENIED`. W011.2 returns `Unsupported` for
PID zero, `PermissionDenied` for access denial, and `ProcessDisappeared` for
`ERROR_INVALID_PARAMETER` opening a nonzero PID. Errors from later APIs are
mapped according to the API and final process-object state; they are not all
treated as disappearance.

The provider requests
`PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_SYNCHRONIZE`, no inheritance,
and no other rights. Query-limited information is required by the image-path
and process-time APIs. `SYNCHRONIZE` is the only additional right: a zero-time
`WaitForSingleObject` gives a direct signaled-state check without the
`STILL_ACTIVE` ambiguity of `GetExitCodeProcess`. No debug privilege, VM
access, or termination right is requested.

The same process handle is used for lifetime checks, creation time, and image
path. A process handle references the process object opened even if its PID is
later reused, so fields from a replacement process cannot be combined in one
inspection. The handle is local RAII state and is closed before the normalized
`ProcessInfo` returns. Creation time is converted from the documented count
of 100 ns units since 1601-01-01 UTC using checked arithmetic.

Microsoft's `Win32_Process` WMI class exposes `CommandLine` as a string and
`GetCommandLineW` retrieves the current process's command line. Neither
provides authoritative structured argv for an arbitrary process. The
documented `CommandLineToArgvW` parser has its own quoting rules and is not
assumed to match every target runtime's argument parsing. WMI/COM was not
introduced solely to add a lossy string. No public mechanism was identified
for querying another process's current working directory. No PEB scraping,
`ReadProcessMemory`, `NtQueryInformationProcess`, PowerShell, or process
enumeration is used.

The API review used Microsoft's documentation for [`OpenProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess),
[process access rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights),
[`QueryFullProcessImageNameW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew),
[`GetProcessTimes`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes),
[`WaitForSingleObject`](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject),
[`GetExitCodeProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess),
[`Win32_Process`](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process),
[`GetCommandLineW`](https://learn.microsoft.com/en-us/windows/win32/api/processenv/nf-processenv-getcommandlinew),
[`CommandLineToArgvW`](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-commandlinetoargvw),
and [Windows path-length limits](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation).
The selected handle APIs do not depend on remote process structure layout;
CI evidence is x64 Windows, and no separate cross-bitness native test is part
of W011.2.

There is no capability-provider/composition API in the current application.
This work records Windows command arguments and working directory as
`Unavailable(ProviderLimitation)` without adding an unused global capability
reporting path. macOS's available working-directory metadata remains intact.

### Error mapping

| Windows condition                                          | W010 result                                   |
| ---------------------------------------------------------- | --------------------------------------------- |
| PID 0 / System Idle Process                                | `Unsupported`                                 |
| `OpenProcess` access denied                                | `PermissionDenied`                            |
| `OpenProcess` invalid parameter for nonzero PID            | `ProcessDisappeared`                          |
| Process object signaled before or after metadata calls     | `ProcessDisappeared`                          |
| Image-path query access denied while process remains alive | Field `Unavailable(PermissionDenied)`         |
| Field API reports unsupported/inaccessible metadata        | Field `Unavailable(Unsupported/Inaccessible)` |
| Malformed successful image path or unnormalizable FILETIME | `ParseFailure`                                |
| Other Win32 query/wait failure                             | `OperatingSystemFailure`                      |
| Bounded allocation failure                                 | `ProviderFailure`                             |

Stable W010 Display text is returned; raw Win32 codes and localized system
messages do not leave the Windows adapter.

### Native test fixture

The Windows integration test spawns the same test executable in a dedicated
test mode. The child writes a readiness marker in a unique temporary
directory, then waits for stdin closure. The parent checks readiness with a
bounded deadline, inspects only this child, closes the pipe, reaps it, and
checks disappearance. RAII cleanup kills and reaps the child if an earlier
assertion fails. This uses neither a shell nor an unrelated runner process.

## Security Considerations

Process handles are opened with limited query plus synchronization access only;
the provider never enables debug privilege or requests VM/termination access.
One Windows-only RAII wrapper owns and closes the handle. Unsafe Win32 calls
remain within the adapter with documented pointer/output/lifetime invariants.
UTF-16 path allocation is bounded and native strings are not converted
lossily. Arguments, paths, and raw Win32 diagnostics are not logged. Metadata
is treated as untrusted local data. No PEB, WMI, shell, or elevation path is
used.

## Platform Considerations

Windows implementation is compiled only under the existing Windows platform
boundary. macOS remains the W011.1 `/ps` and `/lsof` provider, including its
best-effort working directory. Windows reports argv and working directory
unavailable while retaining image path and creation time where accessible.
Protected-process access behavior is mapped but is not a required
environment-dependent native test. PID zero is a special unsupported target.

## Known Limitations

- Windows structured argv and current working directory remain unavailable
  under the selected documented public API strategy.
- A process HANDLE and creation timestamp improve within-inspection identity
  coherence but do not authorize later process actions; future action work
  must reopen and immediately revalidate.
- PID zero is not inspectable as a normal process.
- Native permission behavior for protected targets is not forced in CI.
- Windows evidence is specific to the hosted `windows-2025` x64 runner until
  other versions/architectures are separately tested.
