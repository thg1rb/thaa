# W012.0 — Process Action Safety & Capability Baseline

## Status

In Progress.

## Objective

Define a shared identity-bound process action contract, validate the current
macOS identity evidence, and document honest macOS/Windows action capability
and residual-race semantics before implementing any destructive action.

## Scope

- Add platform-neutral `ProcessAction`, `ProcessActionTarget`, stable outcomes
  and errors, `ProcessController`, and `PlatformCapabilitiesProvider`.
- Require a positive PID and available start time to create an action target.
  Preserve executable path as additional evidence when it was available in the
  observed identity.
- Fail closed if fresh PID/start-time evidence is missing or changed, or if an
  originally available executable path is missing or changed.
- Investigate and adopt macOS `sysctl(KERN_PROC_PID)` for current SDK
  `kinfo_proc.p_starttime`; check process identity before and after the
  existing metadata query.
- Document action capabilities, result meaning, permissions, and residual
  platform risks. Add deterministic tests without invoking process actions.

## Out of Scope

No SIGTERM/SIGKILL, `TerminateProcess`, console control event, `WM_CLOSE`,
controller implementation, Tauri command, frontend/UI, elevation, bulk
operation, automatic escalation, process enumeration, frozen requirement
change, or W012.1/W012.2 implementation.

## Requirements

Establishes safety and platform-capability foundations for FR-008/FR-009 and
NFR-002/NFR-005. It does not implement graceful stop, force stop, or user-facing
process actions. `THAA-REQ-0.1` remains frozen.

## Dependencies

W003 ADR-003 and platform adapter rules; W004 threat model; W006 `ProcessId`,
`ProcessIdentity`, and `PlatformCapabilities`; W010 `ProcessProvider`; W011.1
macOS and W011.2 Windows process evidence. Apply `rust-patterns` and
`security-and-hardening` Project Skills.

## Identity Threat Model

The threat is an observed process exiting followed by PID reuse before the
user requests an action. PID or process-name equality alone does not authorize
an action. Start time is mandatory; executable path is compared when present
in the original observation. Name, arguments, and working directory are
excluded because they can be mutable, presentation-oriented, or unrelated to
process-instance identity. PID zero is rejected because POSIX `kill(0, ...)`
targets the caller's process group and Windows PID zero identifies the System
Idle Process.

`ProcessActionTarget` is constructed from `ProcessIdentity`, has private
fields, and exposes no PID-only controller method. Platform controllers must
revalidate identity immediately before acting. Missing or changed required
evidence is a refusal, never a warning followed by action.

## Windows Capability Investigation

Windows W011.2 returns a precise creation time and executable path from one
limited-information process handle. A future force-stop controller must open
one handle with only query, synchronization, and terminate rights required;
re-read creation time/path and lifetime through that handle; compare the
expected identity; then call `TerminateProcess` through that same handle. It
must not inspect through `ProcessProvider`, close the handle, then reopen by
PID. `TerminateProcess` returns asynchronously; W012.0 semantics report
`Requested` when accepted and do not wait for exit.

`GenerateConsoleCtrlEvent` targets console process groups sharing the caller's
console, and CTRL+C cannot be limited to a selected group. Arbitrary discovered
developer processes do not have a guaranteed console/group relationship.
`WM_CLOSE` addresses a GUI window, which may not exist and may refuse closure.
Therefore Windows graceful stop is unsupported for the generic arbitrary
runtime action. No `taskkill`, PowerShell, console event, window message, or
termination API is invoked.

References: [Microsoft `GenerateConsoleCtrlEvent`](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent), [Microsoft `TerminateProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), [process access rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights), and [closing a window](https://learn.microsoft.com/en-us/windows/win32/learnwin32/closing-the-window).

This describes mechanism readiness for future controllers, not implemented
application actions. Per-target permissions and identity availability can
still refuse a request.

Windows graceful stop as unsupported for the generic target and does not
change the baseline; requirement clarification remains a product/process
decision.

## ProcessController Contract

- `ProcessActionTarget::from_identity(&ProcessIdentity)` validates positive
  PID and available start time; optional observed executable path is retained.
- `ProcessController::request(&ProcessActionTarget, ProcessAction)` accepts
  one explicit `GracefulStop` or `ForceStop`; implementations are synchronous,
  `Send + Sync`, and own fresh platform-specific identity revalidation.
- `ProcessActionOutcome::Requested` means the OS accepted the request, not
  confirmed termination. `AlreadyExited` means the observed instance is no
  longer present. Identity missing/mismatch, permission denial, unsupported
  action, OS failure, and provider failure have safe stable categories.
- `PlatformCapabilitiesProvider` exposes the existing platform-wide
  `PlatformCapabilities`; it does not promise that a particular process is
  actionable.
- A target's `Debug` output omits executable path content to avoid incidental
  path disclosure in diagnostics.
- No wait, retry, or graceful-to-force escalation is part of the contract.

## Revalidation Policy

Compare requested PID and current PID; require exact start-time equality; if
the original identity carried executable path, require the fresh path and an
exact match. Process name is deliberately not compared. Arguments and working
directory never participate. Return `IdentityUnavailable` if required fresh
evidence cannot be obtained, `IdentityMismatch` for changed evidence, and
`AlreadyExited` when the expected process instance is gone. Future Windows
action code must retain one process handle across identity comparison and
native action. Future macOS code must revalidate immediately before signaling
and document the remaining PID race.

## Action Outcome Semantics

An accepted signal or `TerminateProcess` call is a request, not an assertion
that the process exited. W012.0 chooses no bounded wait; the subsequent refresh
observes exit. Graceful and force actions remain separate explicit requests.
No automatic escalation exists. Permission denial never triggers sudo, UAC,
or broader retry. Targets are single positive PIDs only; names, groups,
wildcards, and “all processes on port” are not supported.

## Security Considerations

Action targets require identity evidence and reject PID zero. All shared error
strings are stable and contain no native diagnostics. The macOS shim uses
SDK-defined layout with checked returned size, PID, zombie state, and timeval;
unsafe is restricted to one Rust FFI call with documented pointer invariants.
No process action, privilege escalation, shell, private API, or metadata
logging is added. The remaining macOS PID-to-signal race is explicit.

The only added build dependency is `cc`, used by `build.rs` to compile a tiny
macOS-only C shim against the active SDK headers. This avoids handwritten
`kinfo_proc` layout declarations; it is not linked for Windows. The crate is
already present transitively in the lockfile and is permissively licensed
(MIT/Apache-2.0). No new runtime dependency is added.

## Platform Considerations

macOS API query uses active SDK headers and must execute on both local and
hosted macOS. The platform provider remains target-gated. Windows action
implementation remains deferred; its future force controller must use the
same handle for revalidation and termination. Windows generic graceful stop
is unsupported. macOS/Windows native process actions have not been executed.

## Review Findings

The mandatory read-only review found one P2 issue: the macOS C shim grouped a
zero/incorrect returned size or PID mismatch with confirmed process absence.
The shim now treats only `ESRCH`, a successful zero-length response, or a
zombie process as disappearance. A nonzero unexpected size or PID mismatch
maps to the stable operating-system failure category. Rust status-mapping
tests cover absence, permission denial, success, and unexpected statuses; the
native controlled-child test covers the zero-length/disappearance behavior.
The fix is committed on the PR branch and awaits reviewer re-review.

## Known Residual Risks

- macOS sysctl and signal delivery are separate operations; a narrow PID reuse
  race remains after final identity read. Product accepted this documented
  residual for future action work; it is not a mathematical guarantee.
- `kinfo_proc` is consumed through the SDK headers and is not treated as a
  portable serialized ABI. Each supported SDK/runner must compile and pass
  native provider tests.
- Windows `TerminateProcess` is forceful and asynchronous. Windows generic
  graceful stop cannot safely target arbitrary CLI runtimes with the studied
  APIs.
- macOS `sysctl` evidence is local only until `macos-15` CI passes.
