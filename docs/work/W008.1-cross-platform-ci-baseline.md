## Objective

Establish least-privilege GitHub Actions validation for the existing Thaa code
on shared, macOS, and Windows hosted runners before W009 begins.

## Scope

- Add PR, `develop` push, and manual validation triggers.
- Run shared frontend, documentation, and dependency checks.
- Run Rust formatting, Clippy, and tests on native macOS and Windows runners.
- Run the W008 native listener tests on macOS and build the Tauri app on both
  supported desktop platforms.
- Add the Windows icon resource required by Tauri, generated from the existing
  Thaa application icon without changing its design.
- Document runners, security controls, local equivalents, and platform
  evidence.

## Out of Scope

WindowsPortProvider, Windows networking APIs, product feature or UI/IPC
behavior changes, ProcessProvider/ProcessController, refresh coordination,
Linux product support, release/signing/publishing, dependency automation,
and branch-rule changes.

## Requirements

Establishes validation infrastructure for cross-platform consistency,
reliability, maintainability, and security/dependency verification. W008.1
implements no functional requirement and does not mark Windows listener
discovery implemented.

## Dependencies

W001–W008 are integrated. W004 defines test evidence and merge policy; W005.1
owns format/tooling consistency; W008 supplies the native macOS test suite.

## Design Notes

Use explicit stable GitHub-hosted runner labels: Ubuntu 24.04 x64 for shared
quality, macOS 15 arm64 for native macOS tests, and Windows Server 2025 x64
for native Windows build/tests. Keep shared frontend/docs checks separate
from platform-native Rust validation. Use repository-pinned Rust, Node, and
pnpm versions. Pin actions to verified immutable upstream commits and grant
`contents: read` only. RustSec audits target supported macOS arm64 and Windows
x64 rather than Linux-only dependencies.

The Windows job validates only the current shared code and Tauri build; native
Windows provider tests are added in W009. The macOS job runs W008 tests with
controlled listeners. Branch protection remains unchanged and is documented
as a merge-enforcement gap. The initial Windows build exposed that the W005
scaffold lacked the `icon.ico` resource required by Tauri's Windows resource
compiler. Add that format generated from the existing `icon.png`; the source
icon and product behavior remain unchanged.

## Security Considerations

Workflow definitions are security-sensitive. Use `contents: read`, no project
secrets, no `pull_request_target`, no PR-controlled shell interpolation, no
automatic remediation, and no silent failures. Do not persist checkout
credentials to Git configuration. Review each action and pin it to its
verified upstream commit. Audit advisories require explicit triage; the
workflow must not add ignore entries to obtain a green result.

## Platform Considerations

macOS 15 arm64 hosted CI differs from the local macOS 27 arm64 host. Windows
validation uses a hosted Windows Server 2025 x64 runner, not a self-hosted
physical machine. WindowsPortProvider is absent, so no native Windows
listener behavior or parity is claimed. Linux is used only for shared checks
and is not a supported product target.

## Known Limitations

- Branch protection is not currently configured; successful jobs are not
  enforced by GitHub as required checks. Do not change rules in W008.1.
- Hosted runner images receive weekly software updates within their stable OS
  labels; exact tool versions are emitted in logs.
- The documentation link check verifies local paths, not external URLs or
  heading-fragment correctness.
- Windows native provider behavior remains unimplemented until W009.

Local RustSec 0.22.2 validation against both supported target filters reports
no vulnerability failures. It emits allowed warnings for `proc-macro-error`
(unmaintained) and `glib` (soundness advisory); both are absent from the
macOS arm64 and Windows x64 dependency graphs according to `cargo tree`. The
CI log must retain these warnings for later dependency review.
