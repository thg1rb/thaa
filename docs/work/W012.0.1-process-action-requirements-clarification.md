# W012.0.1 — Process Action Requirements Clarification

## Status

In Progress.

## Objective

Resolve the process-action capability ambiguity in `THAA-REQ-0.1` using the
verified platform findings recorded in W012.0, before either native controller
is implemented.

## Scope

- Clarify affected product guidance and requirements FR-008/FR-009 and
  PR-005/PR-006 through the documented reviewed requirement-change process.
- Keep the `THAA-REQ-0.1` identifier and stable requirement IDs; record this
  as an explicit, traceable change to that baseline.
- Define distinct Graceful Stop and Force Stop intent and platform capability
  expectations.
- Update architecture, security, test planning, and traceability documents.

## Out of Scope

No process termination, SIGTERM/SIGKILL, `TerminateProcess`, native
`ProcessController`, Tauri command, frontend/UI, automatic elevation,
automatic force escalation, or W012.1/W012.2 implementation.

## Requirements

This is a requirements clarification for FR-008/FR-009 and PR-005/PR-006.
It does not mark process actions implemented. W012.1 owns macOS graceful and
force controllers; W012.2 owns Windows force controller. Windows generic
graceful stop is unsupported under the current capability model.

## Dependencies

W002 requirement freeze/change governance; W003 ProcessController and
platform-capability architecture; W004 process-action threat model; W012.0
identity and native capability evidence. The task instruction authorizes the
product-owner scope review required by the existing change process.

## Requirement Change Record

The baseline change procedure in `docs/requirements/PRODUCT-RULES.md` directs
reviewed requirement-change PRs to record rationale, affected IDs, acceptance
criteria, scope/platform/security/test effects, traceability, and dependencies,
and explicitly says to update the frozen baseline deliberately. No separate
amendment numbering convention exists. Therefore this work retains baseline
identifier `THAA-REQ-0.1`, preserves the prior wording in Git history, and
records the clarification in Product Rules rather than inventing `0.2`.

The ambiguity came from product-scope wording “graceful stop with explicit
force-stop fallback” and FR-009's “force stop as a separate, explicit
fallback.” FR-008 already conditioned graceful stop on platform/provider
support, but the broader fallback phrasing could imply graceful-stop parity or
force-as-graceful substitution. W012.0 verified that macOS has both a generic
graceful and force mechanism, while Windows has no safe generic graceful
mechanism for arbitrary discovered developer processes. The clarified
requirements make capability availability explicit and preserve force stop as
a separate user-requested action.

## Design Notes

- Graceful Stop requests normal shutdown/cleanup. It is exposed only when the
  platform capability reports generic support. Unsupported returns
  `Unsupported`; it never invokes Force Stop.
- Force Stop requests forced termination and remains separately explicit and
  confirmed. macOS expects SIGKILL; Windows expects `TerminateProcess` through
  the same HANDLE used to revalidate identity.
- macOS expects SIGTERM for Graceful Stop, with positive PID and freshly
  verified start time. The check-to-signal PID-reuse race remains documented.
- Windows generic graceful stop remains unsupported: console control events
  cannot safely target arbitrary discovered runtimes; `WM_CLOSE` requires a
  GUI window. Neither mechanism is required by the generic action contract.
- Every action requires `ProcessActionTarget`; PID-only targeting is
  prohibited. macOS requires PID and start time. Windows requires PID,
  creation time, and executable path when included in the original identity.
  Missing or changed required evidence refuses action; an absent process is
  `ProcessActionOutcome::AlreadyExited`.
- `Requested` means OS acceptance, not confirmed exit. No automatic wait,
  retry, force escalation, sudo/UAC, or privileged helper is required. Actions
  target one process only; group and bulk termination are prohibited.
- `PlatformCapabilities` uses the existing `graceful_stop` and `force_stop`
  `CapabilitySupport` fields. Expected generic values: macOS Supported /
  Supported; Windows Unsupported / Supported. Capability does not guarantee
  per-process permissions or eliminate identity checks.
- Future UI/API behavior must expose only supported actions or report them as
  unavailable. Both platforms need not show the same controls.

## Validation

Documentation-only gates: Prettier check for maintained documentation paths,
`pnpm docs:check`, manual requirement ID/traceability review, and
`git diff --check`. PR CI must pass Shared Quality, macOS Native Validation,
and Windows Native Validation, including existing W008–W011 native provider
tests. No destructive native action tests are run in this work item.

## Security Considerations

Identity mismatch or missing required identity evidence fails closed. No
action by PID/name/group/port, silent Force Stop fallback, automatic
escalation, or privilege elevation is permitted. Platform residual races and
target-specific permission failures remain explicit. This work adds no native
action code or process metadata handling.

## Platform Considerations

macOS graceful and force action requirements remain Supported, with the
W012.0-documented PID-to-signal race. Windows generic graceful stop is
Unsupported; force stop is Supported only with same-HANDLE identity
revalidation and action. Capability reporting is platform-wide and does not
promise that a particular process can be acted on.

## Known Limitations

W012.0.1 does not implement either platform controller or the UI. macOS
retains a narrow identity-check-to-signal PID reuse race. Windows generic
Graceful Stop remains unavailable; any specialized GUI/console action would
require separate capability requirements and safety review. A successful
request does not confirm process exit.
