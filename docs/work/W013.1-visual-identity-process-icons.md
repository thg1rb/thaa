# W013.1 — Visual Identity & Process Icon Enrichment

## Status

Implementation and the requested visual-acceptance refinement are on

## Objective

Give Thaa a restrained technical visual identity and show native application
icons where supported, without changing runtime discovery or process-action
identity and safety.

## Scope

- Establish reusable visual tokens with cyan/teal reserved primarily for
  interaction, and separate danger/warning/success colors.
- Redesign runtime cards, loading/empty/status presentation, and Force Stop
  confirmation for responsive desktop use and accessibility.
- Add optional platform-boundary process icon enrichment and snapshot-scoped,
  bounded presentation transport.
- Provide Thaa fallback marks for unresolved process icons and unknown owners.
- Update design, platform, architecture, security, and test documentation.

## Out of Scope

W014 search/filter, third-party brand assets, private macOS APIs, framework or
runtime detection, project/Git details, resource metrics, process trees, and
changes to `ProcessIdentity`, `ProcessActionTarget`, or `ProcessController`.

## Visual Direction

Use graphite surfaces, fine structural borders, selective corner cuts, compact
technical labels, and restrained interaction glow. Interface copy and runtime
identity remain readable; no continuous glitch or decorative scanline effects
are used. Cyan/teal is the interactive primary, while Force Stop remains danger
colored. Motion respects `prefers-reduced-motion`.

## Icon Architecture

Icons are presentation enrichment behind a platform-specific adapter. macOS
uses public AppKit `NSRunningApplication` icons where a running application
icon exists. Windows extracts an icon from the executable path returned by
`WindowsProcessProvider`. CLI processes, unknown owners, unsupported paths,
and any lookup/conversion failure use Thaa fallbacks. No third-party brand
mapping is bundled.

Runtime snapshots return before platform icon work starts and include
snapshot-scoped references for successfully inspected processes. The UI then
calls `get_runtime_process_icons(generation)` on a blocking worker; it passes no
PID or path. The backend resolves the current generation's observed process
metadata, one lookup per process, validates and bounds PNGs, and caches the
result only for that generation. The frontend keeps its Thaa fallback visible
while this optional request is pending. Stale generations return no assets.
Icon failure cannot fail a scan or hide a runtime.

## Platform Notes

The public AppKit icon is application-instance enrichment and does not promise
coverage for command-line/background processes. Windows Shell extraction may
return no icon for binaries without embedded resources. Windows native icon,
bitmap, and GDI resources remain within the Windows adapter and must be released
on all paths. No private macOS API or frontend-supplied filesystem path is used.

## Testing

Test presentation association, unresolved/unknown fallback, malformed or
oversized payload rejection, per-snapshot deduplication, stale-generation
refusal, and failure isolation with deterministic doubles. macOS native testing
uses a controlled command-line child to verify fallback behavior. Windows
native testing extracts an icon from the OS `shell32.dll` resource and validates
the bounded PNG conversion path. Existing W008–W013 tests and all
Shared/macOS/Windows CI remain required. Manual visual inspection and user
acceptance are mandatory before merge.

Local native evidence includes a controlled `/bin/sleep` child resolving to the
Thaa fallback icon, plus W013-controlled `node` listener tests for Graceful and
Force Stop. The real debug application displayed the redesigned runtime list,
status hierarchy, controls, and destructive confirmation. No GUI application
icon success test is deterministic on hosted macOS because CI does not provide a
controlled signed GUI application fixture. Windows native testing uses the OS
`shell32.dll` icon resource; local Windows cross-target validation is
unavailable because the host lacks `llvm-rc`.

## Security and Accessibility

Icon bytes never enter process identity or action authorization. Native icon
resolution accepts only backend-observed process metadata, has fixed output
size and aggregate byte limits, and never executes target code. Runtime
metadata remains unlogged. Keyboard operation, visible focus, contrast,
semantic states, non-color cues, decorative icon semantics, and reduced-motion
support remain required.

## Visual Acceptance Refinement

The refinement replaces transient action banners with a shared Toast viewport.
It uses polite announcements for success/information and assertive alerts for
errors, shows at most three Toasts with a bounded queue, allows keyboard
dismissal, pauses expiration while hovered/focused, and avoids notifications
for passive refreshes. A process-action success continues to say that the
request was sent and will be checked later; it does not claim the process has
exited. The old persistent banner remains only for incomplete/stale scan state
and the initial/global scan failure, where retry stays available.

React responsibilities are organized under `features/runtime-inspector`:
the page composes focused components and hooks, while command names and Tauri
`invoke` transport live in `api/runtimeClient.ts`. Shared notifications live
under `shared/ui/toast`; `App.tsx` is the provider/page composition root. A
synthetic development-only preview can show success/error Toasts and sample
cards; it does not call native inspection or process-action APIs.

The macOS main window uses the supported Tauri `Overlay` title-bar style,
retains native traffic lights, hides redundant native title text, and has an
explicit non-interactive drag region above content. The native window
background is set to `#080e13`, synchronized with the CSS canvas applied to the
webview document root (`html`, `body`, and `#root`). The document is the only
vertical scroll owner and vertical overscroll is suppressed; other platforms
retain their native title bars. No transparent window/private API is used.

## Toast and Skeleton refinement

The Toast viewport now anchors to the bottom-right. Items remain ordered from
oldest at the top to newest at the bottom. Timeout and manual close change an
item to an exiting phase; animation completion removes it and promotes the
oldest queued item. A bounded fallback timer handles missing animation events.
The visible Toast limit and FIFO queue remain bounded, hover/focus still pauses
the reading duration, and reduced-motion settings reduce the transition to a
near-instant fade.

The initial scan now displays three noninteractive Runtime Card Skeletons,
with muted header count and timestamp placeholders. Skeletons are hidden from
assistive technology while one polite live status describes the scan. An
initial error or empty result replaces them with the existing error or empty
state. Refreshing a snapshot never replaces valid Runtime Cards with
Skeletons.

Optional process icon resolution remains independent from the runtime scan.
Known-process icon slots show a fixed-size Skeleton until that snapshot's icon
request completes, then display the native icon or Thaa fallback. Unknown
owners use their fallback immediately. A development-only preview supports
initial-card and icon-loading states for visual inspection and is not included
in production assets.

Automated coverage now includes initial skeletons, resolved/fallback icon
states, refresh with retained content, timeout exit, manual exit, queue
promotion, and ordering. Manual visual acceptance remains pending; PR #33 stays
open and W014 has not started.

## Review Findings

The read-only review identified two P2 issues: native icon extraction was on
the critical runtime-snapshot path, and the Windows icon test could pass
without exercising extraction/conversion. Resolved by moving icon retrieval to
a separate generation-scoped command and requiring a bounded PNG extracted
from the Windows system icon resource. Re-review then identified that
`ExtractIconExW`'s documented `UINT_MAX` failure sentinel needed an explicit
check. The adapter now adopts the returned handle only when exactly one icon
was reported, with deterministic count-mapping tests. The icon extraction fixes passed re-review and hosted validation before this
refinement. The current Toast/Skeleton re-review also reported no actionable
findings.

## Known Limitations

Native icon availability depends on platform metadata. macOS CLI/background
processes may have no `NSRunningApplication` icon. Windows binaries may have no
embedded icon. Both conditions deliberately show a Thaa fallback.

## Application and tray branding integration

The approved 1024×1024 application master and 512×512 tray masters remain
unchanged in `src-tauri/icons/source/`. Apple’s current HIG describes a square
1024×1024 macOS icon canvas, centered primary content, current production
templates, and layered Icon Composer workflows; it does not prescribe an
824px body. For this repository’s existing flattened Tauri `.icns` workflow,
Thaa uses an 824×824 body centered on the 1024×1024 canvas, with 100px
transparent margins. This is the selected flattened-icon geometry, not a claim
that Apple requires that exact inset. The supplied artwork already includes
its designed rounded-square enclosure, so the generator adds no second mask.

The deterministic CoreGraphics generator creates production derivatives in
`src-tauri/icons/derived/`. It verifies an asymmetric four-color orientation
fixture through bitmap drawing and an in-memory PNG encode/decode round-trip,
then checks the app’s exact alpha bounds `(100,100)..(923,923)` before writing.
The previous vertical inversion came from applying a y-axis flip when drawing
the decoded `CGImage` into a top-to-bottom bitmap context; removing that extra
flip preserves the PNG’s upright orientation. Tray alpha bounds are
`(57,102)..(455,410)` (399×309). The macOS monochrome glyph is fitted
proportionally at 32px high in a 44×44 transparent canvas, with alpha bounds
`(1,6)..(42,37)`; the Windows cyan glyph remains 23px high in a 32×32 canvas,
with alpha bounds `(1,4)..(30,27)`. No stretching or artwork redesign is used.

The pinned Tauri icon generator consumes the derived application master and
regenerates the standard application set, including `.icns` and `.ico`. The
existing Rust `TrayIconBuilder` selects the appropriate derived tray image
through compile-time target cfgs; macOS uses native template recoloring and
Windows uses its cyan icon normally. Branding remains separate from runtime
process icons and action identity.

Source alpha analysis before this sizing pass found the app artwork occupied
the full 1024×1024 bounds, while tray artwork occupied 60.4% of the 512px
source height. The new production composition uses the requested fixed 824px
body rather than percentage candidates. At 32px glyph height the 1.291:1
source aspect ratio requires about 41.3px width; the selected 44px canvas leaves
about 1px per side after rasterization and keeps the symbol inside the native
image. The canonical source SHA-256 values verified unchanged are:

- App: `7a1c8b5ebbc7859e3d7bc47b1b3e7f795eaf104522d0d3e432a99acb73689062`
- macOS tray: `c0ed84b6f11d0b188ad660d921cc52fd27a67f251814bbc339d5e57e56c4e955`
- Windows tray: `95de2cdfd511fc7e85558b7a7d0f39538dbeab4c4f631bf6597025f7c249a035`

The `source/README.md` records the generation command and selected dimensions.
Official design references are Apple’s [App Icons HIG](https://developer.apple.com/design/human-interface-guidelines/app-icons),
[Icon Composer creation guide](https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer),

## API References

The adapter uses Apple's public [`NSRunningApplication`](https://developer.apple.com/documentation/appkit/nsrunningapplication)
lookup and [`icon`](https://developer.apple.com/documentation/appkit/nsrunningapplication/icon)
surface. Windows resource handling follows Microsoft documentation for
[`ExtractIconExW`](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-extracticonexw),
[`DestroyIcon`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-destroyicon),
and [`GetIconInfo`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-geticoninfo).
