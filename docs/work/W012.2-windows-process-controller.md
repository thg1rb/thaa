# W012.2 — Windows Process Controller

## Status

In Progress. Implementation and deterministic/local regression validation are
underway; native Windows CI, read-only review, and merge are still required.

## Objective

Implement Windows Force Stop against the shared identity-bound
`ProcessController` contract. Generic Windows Graceful Stop remains
unsupported under the W012.0.1 clarification.

## Scope

- Add `WindowsProcessController` and accurate Windows action capabilities.
- Reuse W011.2 process HANDLE ownership, creation-time, executable-path, and
  lifetime helpers.
- Open one process HANDLE per Force Stop request, validate required identity
  through that HANDLE, and call `TerminateProcess` through the same HANDLE.
- Return `Requested` after API acceptance; leave exit confirmation to fresh
  observation.
- Add native controlled-child tests and update architecture, security, testing,
  and traceability documentation.

## Out of Scope

No generic Windows Graceful Stop, Tauri IPC, frontend action UI, process-tree
or bulk termination, automatic elevation, retry, wait-for-exit, automatic
escalation, or changes to macOS controller behavior.

## Requirements

Implements the Windows Force Stop backend expectation in FR-009. Windows
Graceful Stop is unsupported per FR-008 and W012.0.1. Force Stop requires a
positive identity-bound target, current creation-time match, and executable
path match whenever the observed identity included a path. It fails closed on
missing or conflicting evidence. An accepted request is not confirmed exit.

## Identity Safety Model

The controller opens the requested PID once with
`PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_TERMINATE | SYNCHRONIZE`. The
same HANDLE anchors before/after lifetime checks, `GetProcessTimes`, optional
`QueryFullProcessImageNameW` comparison, and `TerminateProcess`. It never
reopens the PID after validation. Creation time always must match; an observed
executable path must also be available and equal. Name, arguments, and working
directory are not authorization evidence. A process HANDLE refers to the
original process object even if the numeric PID is later reused; this protects
the action sequence from retargeting a replacement process. It does not
eliminate PID reuse globally or replace future action-time revalidation.

## HANDLE Lifetime Model

W011.2's internal `OwnedProcessHandle` is shared from the Windows-only
`process_native` module. It is non-Clone/non-Copy and closes exactly once in
`Drop`. It never escapes the adapter or survives the controller call. All
early returns retain RAII cleanup.

## Access Rights

The action requests only query-limited-information, terminate, and synchronize
rights. The latter supports nonblocking zero-timeout process-state checks. No
VM access, `PROCESS_ALL_ACCESS`, debug privilege, elevation, or retry with
broader rights is used. Graceful requests return `Unsupported` before opening
a handle.

## Termination Semantics

Force Stop calls `TerminateProcess` with fixed exit code `1`. A successful
return means Windows accepted the asynchronous termination request and maps to
`Requested`; production does not wait. Test code waits with a bounded timeout
on its own controlled child. Windows generic Graceful Stop is unsupported and
never falls back to Force Stop.

## Error Mapping

| Native condition                                                      | Shared outcome                                            |
| --------------------------------------------------------------------- | --------------------------------------------------------- |
| Nonzero target PID fails `OpenProcess` with `ERROR_INVALID_PARAMETER` | `AlreadyExited` (same context-specific mapping as W011.2) |
| `ERROR_ACCESS_DENIED` during open/action                              | `PermissionDenied`; no elevation                          |
| Same-HANDLE process object is signaled                                | `AlreadyExited`                                           |
| Creation time or required path differs                                | `IdentityMismatch`; no termination call                   |
| Required identity unavailable                                         | `IdentityUnavailable` or specific permission failure      |
| `TerminateProcess` succeeds                                           | `Requested`                                               |
| Other native failures                                                 | stable `OperatingSystemFailure` / provider error          |

Raw localized Windows error text, HANDLE values, paths, and process metadata
are not emitted in diagnostics.

## Native Tests

The Windows integration test launches a test-owned copy of its own test binary
in a controlled fixture mode and coordinates readiness via a private temporary
file and stdin. It verifies accepted force request and exit code `1`, creation
time mismatch refusal with child survival, executable mismatch refusal with
child survival, Graceful Stop unsupported with child survival, and an already
exited target. Fixture cleanup terminates/reaps only its own child. A bounded
wait is test-only. These tests must execute on the native `windows-2025` CI job.

## Security Considerations

No process action is possible through PID alone. The controller has no
`PROCESS_ALL_ACCESS`, VM read, debug privilege, automatic elevation, shell,
WMI, `taskkill`, console event, or window message path. Same-HANDLE validation
is mandatory; mismatch and missing evidence fail closed. No termination
request is retried or redirected to a replacement PID. Child-action tests
target only fixture-owned processes.

## Platform Considerations

macOS implements Graceful Stop with `SIGTERM` and Force Stop with `SIGKILL`,
but retains a narrow sysctl-to-PID-signal race. Windows supports Force Stop
through same-HANDLE revalidation and `TerminateProcess`; generic Graceful Stop
remains unsupported. Both controllers return request acceptance, not exit
confirmation. Sandboxed, App Store, and packaged distribution behavior is not
validated here.

## Known Limitations

- A process can exit between the final same-HANDLE state check and
  `TerminateProcess`; the HANDLE still refers to the same object, so this does
  not retarget a replacement PID.
- Access to protected processes can be denied under ordinary user rights.
- Windows Graceful Stop is unsupported for generic arbitrary discovered
  processes.
- No Tauri command or user-facing action flow exists until W013.
- Distribution and sandbox behavior is not validated.
