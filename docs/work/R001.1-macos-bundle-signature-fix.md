# R001.1 — macOS Bundle Signature Incident Fix

**Status:** Fix integrated; v0.1.1 candidate frozen; XProtect triage in progress
**Parent:** R001 — Closed Alpha / Early Preview Release Readiness  
**Affected release:** Thaa `v0.1.0`  
**Corrective release target:** Thaa `v0.1.1`

## Incident record

Discovered 2026-10-06 from tester-driven Gate B evidence. The exact published
macOS artifact, `Thaa_0.1.0_aarch64.dmg`, was downloaded and its SHA-256 matched
the published value:

```text
4365f2a0d91ef5865f3aaad953fdce004c80ed8425272af9ad2c5af8fb438297
```

After copying `Thaa.app` to `/Applications`, macOS reported “Thaa is damaged
and can’t be opened.” The user's strict verification returned:

```text
code has no resources but signature indicates they must be present
```

`syspolicy_check distribution` also reported that the code signature did not
fully cover `Info.plist`. Its `Adhoc Signed App` and `Notary Ticket Missing`
findings are expected for the accepted zero-budget distribution; they are not
the incident defect.

Severity is **Release-critical — macOS distribution defect**. The published
macOS package is not suitable for normal tester distribution. Windows is not
implicated by current evidence: its v0.1.0 NSIS package, checksum, and
automated validation remain as recorded in the parent R001 record. No Windows
interactive test is claimed.

## Investigation and root cause

The exact public DMG was downloaded from the v0.1.0 release. Its SHA-256
matched the release and `hdiutil verify` passed. Strict verification of the
app mounted from that image reproduced the failure. `codesign -dv` reported
`flags=0x20002(adhoc,linker-signed)`, `Info.plist=not bound`, and
`Sealed Resources=none`; `Contents/_CodeSignature/CodeResources` was absent.

The checked-in Tauri configuration had no `bundle.macOS.signingIdentity`.
Tauri therefore left only the executable's linker ad-hoc signature and did
not seal the complete `.app` bundle. No project post-signing hook or resource
mutation step was found. The DMG is not the cause: the invalid signature is
present in the exact app extracted from the published DMG. Root cause is the
missing explicit ad-hoc app-bundle signing identity, combined with CI checking
executable metadata instead of verifying the bundle.

The prior R001 sections documenting the old CI interpretation are retained as
historical evidence. This incident record supersedes their conclusion that
bundle-level verification was inapplicable to the unsigned path.

## Corrective implementation

Tauri configuration now selects the supported ad-hoc bundle identity `-`.
The release packaging script builds the `.app`, verifies its strict signature,
copies that exact bundle into a DMG staging directory, verifies the staged
copy, creates the DMG, mounts it, verifies the final mounted app, and compares
the `Info.plist`, executable, `icon.icns`, and `CodeResources` hashes against
the verified source app before generating SHA-256. It requires a sealed
`CodeResources` file and the expected version, icon, architecture, ad-hoc
signature, and missing Team ID. `syspolicy_check` is diagnostic and may still
report ad-hoc signing and a missing notary ticket.

Local packaging validation ran on Apple Silicon macOS 27.0.1; this was a
developer host, not a clean-install environment. It built the release-profile
`0.1.1` app and DMG. Tauri logged signing with identity `-` for the executable
and enclosing app. Strict verification passed before packaging, on the staged
bundle, and on the app mounted from the generated DMG. The mounted bundle
reported `Info.plist entries=14`, `Sealed Resources version=2`, 13 rules, and
one sealed file. `hdiutil verify`, mounted app verification, source-to-mounted
file comparisons, and checksum verification passed. The latest local DMG hash
was `030d8f9bd0365819d03aa45b69f2e8b1d34ef8ce30ad47f8e51e94a056ffa224`; this
is a local implementation check, not a release candidate. The regression
script was also run against the exact v0.1.0 DMG and rejected its missing
`CodeResources` file before strict verification. `syspolicy_check`
reported only the expected ad-hoc and missing-notarization distribution
findings; no invalid-signature or Info.plist-coverage defect remained.

## Regression prevention

- macOS PR CI and future candidate packaging use the same package script.
- Strict `codesign --verify --deep --strict --verbose=4` is mandatory before
  DMG creation and on the exact app mounted from the final DMG.
- The app copied into the DMG is the app verified before packaging; hashes of
  signature-covered files are compared after mounting.
- Windows NSIS remains independently validated at version `0.1.1`.

is not an acceptance method.

### Local macOS 27 comparison

The same hash-verified v0.1.1 DMG and published v0.1.0 DMG were mounted on the
local Apple Silicon host: macOS `27.0.1` build `26A434`, Darwin
`27.0.0`, Xcode `27.0` build `27A266a`, Apple clang `21.0.0`. Candidate,
historical, and control DMGs/apps had no `com.apple.quarantine` attribute in
this Actions-artifact download context.

`syspolicy_check distribution` was run three times against the exact mounted
v0.1.1 app and three times against a minimal locally compiled, ad-hoc-signed
control app. Each returned exit `70` with only `Adhoc Signed App` and `Notary
Ticket Missing`; none reported `Internal Xprotect Error`. The control bundle
passed strict `codesign` and was not executed. The same diagnostic was run
once on the exact v0.1.0 app: it reported both original `Codesign Error`
findings (missing resource seal and incomplete `Info.plist` coverage), plus
the expected ad-hoc/notary findings; it did not report an XProtect error.
This comparison preserves the distinction between the fixed v0.1.0 bundle
defect and the new XProtect diagnostic.

The candidate bundle inventory contained `Info.plist`, the arm64 Mach-O main
executable, `icon.icns`, and `_CodeSignature/CodeResources`; no other Mach-O,
helper, framework, or nested executable was found. The candidate strict
verification passed and signature metadata reported `Signature=adhoc`,
`TeamIdentifier=not set`, and a valid sealed-resources section.

Filtered, time-bounded local unified logs showed XProtect AnalysisService XPC
connections, SystemPolicy database read/write denial with read-only fallback,
notarization-daemon error 3, and a `SecAssessmentCreate` `-50` error for a
PST assessment. The paths were private/redacted and no XProtect rule or
candidate file was identified. `softwareupdate --history` exposed no
matching XProtect/Security Data/Gatekeeper entry. These local logs are not
evidence about the hosted macOS 15 runner.
