# v0.1.0 Release Credential Checklist

This checklist describes optional trusted-distribution hardening and the
release controls used by `.github/workflows/release.yml`. The zero-budget
`v0.1.0` path is unsigned and requires no paid signing credential. Never commit
credentials, print them in CI, or paste secret values into issues or work
records.

## GitHub environments

Use GitHub environments where they add approval/secret protection and are
available without paid infrastructure. The unsigned candidate path does not
use the signing environment. Configure these environments before using the
trusted or publish path:

| Environment       | Protection                              | Allowed ref              | Purpose                                                                      |
| ----------------- | --------------------------------------- | ------------------------ | ---------------------------------------------------------------------------- |
| `release`         | Required reviewer; branch rules enabled | `main` workflow dispatch | Restricts macOS signing/notarization secrets to the trusted release workflow |
| `release-publish` | Required reviewer; branch rules enabled | `main` workflow dispatch | Approval gate for publishing the GitHub pre-release                          |

Dispatch the workflow definition only from `main`. Candidate mode builds the
exact dispatched `main` commit and prints its immutable SHA in the summary.
Record the successful candidate run ID as well. Publish mode requires the
accepted candidate SHA and run ID, validates that the run completed the
unsigned macOS/Windows jobs on `main`, and reuses those exact artifacts and
checksums (retained for 90 days). It also verifies that `v0.1.0` points to that
same commit on `main`. The publisher rechecks the tag immediately before
release creation. Configure a public-repository tag ruleset for
`v0.1.0` that restricts creation and blocks updates/deletion. GitHub documents
repository rulesets as available on Free for public repositories; if repository
administration shows that a needed rule is unavailable, record the restriction
and require release-owner verification of the exact source SHA and tag before
publication instead. See [GitHub ruleset availability](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

## Deferred macOS Developer ID signing and notarization

Developer ID signing, Apple notarization, and stapling are **deferred release
hardening**, not blockers for the zero-budget `v0.1.0` Early Preview. The
candidate/release workflow's explicit trusted mode retains this support and
fails closed if selected without all required credentials. Unsigned mode is
the default and does not read signing secrets or require the `release`
environment.

| Item                                                  | How to obtain / configure                                                                                                                                                                    | GitHub name                                                                                                                                                                    | Needed for                                              |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| Apple Developer Program membership                    | Enroll through [Apple Developer Program](https://developer.apple.com/programs/whats-included/); Apple currently lists USD $99/year (regional pricing may vary).                              | Account is configured outside Actions                                                                                                                                          | Future Developer ID distribution; not needed for v0.1.0 |
| Developer ID Application certificate with private key | Create in Certificates, Identifiers & Profiles and export certificate plus private key as a password-protected `.p12`. Encode the file as one-line base64 locally. Do not commit the `.p12`. | Environment secret `APPLE_CERTIFICATE` (base64 P12)                                                                                                                            | Future signed macOS DMG                                 |
| P12 import password                                   | Choose when exporting the `.p12`; store only in the protected environment.                                                                                                                   | Environment secret `APPLE_CERTIFICATE_PASSWORD`                                                                                                                                | Future signed macOS DMG                                 |
| Signing identity                                      | Exact Developer ID Application identity name as shown by Keychain/codesign.                                                                                                                  | Environment variable `APPLE_SIGNING_IDENTITY`                                                                                                                                  | Future signed macOS DMG                                 |
| Apple Team ID                                         | Team identifier from the Apple developer account.                                                                                                                                            | Environment variable `APPLE_TEAM_ID`                                                                                                                                           | Future signature verification                           |
| App Store Connect API key                             | Create a key with the role/access required for notarization in App Store Connect. Download the `.p8` private key once and keep it secure.                                                    | Environment variable `APPLE_API_KEY` for Key ID; environment variable `APPLE_API_ISSUER` for Issuer ID; environment secret `APPLE_API_KEY_P8_BASE64` for base64 `.p8` contents | Future notarization and stapling                        |

The trusted workflow uses API-key authentication. It does not require an Apple
ID password or app-specific password. The runner writes the decoded API key
only under its temporary directory with owner-only file permissions. Tauri
imports the certificate for the build; no persistent keychain or signing
material is stored in the repository. No trusted signature, notarization,
stapling, or Gatekeeper result is claimed for the zero-budget release.

## Windows signing

The approved R001 choice is an **unsigned Windows 11 x64 NSIS installer for
selected testers**, with explicit SmartScreen and Smart App Control disclosure.
No Windows signing credential is required for this chosen closed-alpha path.
Smart App Control or enterprise policy may block the package entirely; never
recommend disabling those protections.

Authenticode is **deferred release hardening**, not a blocker for the accepted
unsigned selected-tester package. Revisit commercial certificates or suitable
open-source signing options in a later release decision. No certificate or
signing secrets are configured. Smart App Control or organization policy may
still prevent some testers from installing the unsigned build.

## Post-v0.1.0 release-hardening backlog

- macOS: Apple Developer Program enrollment, Developer ID Application signing,
  App Store Connect API key, notarization, stapling, and Gatekeeper trusted-
  distribution validation.
- Windows: choose a sustainable Authenticode/open-source signing strategy,
  validate a signed installer, and perform interactive clean-machine and soak
  testing.

## Current credential status

- Zero-budget macOS package: unsigned/ad-hoc, not notarized; this is the
  selected v0.1.0 policy, not a signing failure.
- Developer ID/notarization and Windows Authenticode: **DEFERRED RELEASE
  HARDENING**; no signing credentials are configured. The optional future
  trusted mode requires the listed Apple credentials. Before setting any
  signing secrets or selecting trusted mode, configure and verify protection
  on the separate `release` GitHub environment; it currently has no reviewer
  protection rules.
- GitHub publication: candidate runs do not create a tag/release or distribute
  public assets. The final publish path is manually selected and protected by
  the `release-publish` environment, which currently requires owner review,
  does not allow administrator bypass, and permits deployment from `main`.
